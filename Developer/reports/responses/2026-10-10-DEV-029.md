# DEV-029：run_cmd 旧 SELinux getter 凭据槽位匹配修复

角色：Developer；2026-10-10。来源为 [Tester 4.4 加载报告](../../../Tester/reports/runs/2026-10-10-re_kernel-and-rekx-4.4-legacy-kp%231.md)，测试中的 run_cmd_demo 普通/debug 两份在 task getter 推导时返回 `-ENOENT`（0/2）；rek、rekx 的加载、ping、卸载通过是该报告的实机结论。本响应提供实现方修复及离线自检，问题仍待独立复核。

## 问题与修复

- 问题编号：DEV-029；归属：Developer；发现方：Tester。
- 严重度：中（目标旧内核加载兼容性缺口）；frequency：已观察 2/2；confidence：已确认。
- 状态：工作树修复，待冻结与独立复核。关闭条件：独立核对两个凭据槽位和后续读取链，核验新冻结身份，再由 Tester 验证加载及命令执行。

B2N 的 getter 在入口索引 7～9（从 0 起）读取 `task+0x7a8 → cred+0x78 → security+0x4`，随后把 SID 写入输出参数。Tester 记录的 KP 字段标签为 `cred_offset=0x7a8`、`real_cred_offset=0x7b0`。原匹配仅接受后者，因此跳过真正读取链。

`rc_offsets.c` 现在接受运行中 KP 已知的 `cred_offset` 或 `real_cred_offset`。仍在前 16 条指令里核对任务基址、连续两级指针、32 位 SID 读取及同寄存器输出写回；KP 已知的 `cred.security` 继续交叉核对。BTF、现代 cred getter、worker 布局和命令执行路径沿用原实现。

这里只使用 KP 提供的两个槽位作为锚点；不根据日志标签推定所有 KP 的语义顺序。偏移仍来自目标指令链，不能仅凭换用旧 KP SDK 重新编译消除这处运行时匹配错误。

## 离线复现与 Oracle

指定语料为 `B2N-416G_boot.img`，boot SHA-256 `ea919143cb1f057f3d35d726294166d5186f376e9751941b83940e75d48a288c`，Image SHA-256 `7633fbac5ce30b726a1acdbf57f730aa847a9510984a25bc23f9ddcdb0956e1c`。复用已验证的 Image 和符号表，新增输出目录。

旧离线参考把 `0x7a8` 填入 `real_cred`，没有模拟这次运行端 KP 的两个偏移。此次宿主夹具增加 SDK 已有的 `cred_offset` 字段，镜像探针分别输入 `real_cred=0x7b0`、`cred=0x7a8`；历史参考与收据保留。以修复前生产代码运行新输入，`calculate_offsets()==0` 断言失败；同样输入运行修复后生产代码，通过并得到：

```text
instruction fields: path=0x28 security=0x78 sid=0x4 worker_size=40
run_cmd production async/credential/offset tests passed
```

原 185 条 assert 全部按原顺序保留，新增 6 条 assert（两个槽位正例循环及五个负例：未知槽位、security 基址断链、输出参数错误、已知 security 冲突、有效链位于窗口外）。ASan/UBSan 宿主回归通过。没有删减或放宽既有断言；夹具输入补全属于本次复现依据，仍需 Auditor 独立复核。
