## 质疑

### 有效性

交付绑定仍检查实例、源提交、指纹、产物哈希、签名及源码内容。用内容比对替代祖先关系符合压平发布的用途：祖先关系本身不能保证后继提交未改源码。有限反例确认，已记录的共享输入缺失和伪造绑定会被拒绝。

但模块路径在源码和交付提交中都不存在时，两个 Git 查询失败都变成空字符串，相等判断会接受它们。另有报告历史版本缺提交时，被错误替换成当前字节，造成错误的追加哈希失败。两项见下文正式问题。

### 简洁性

删除文本关键词检查、合并报告遍历和取消兼容字段的命名硬要求都有记录。可以保留这些改动。修复应限于正确处理查询失败和历史字节缺失，无需恢复祖先要求、增加 KernelPatch 版本绑定或重新添加关键词扫描。

### 后果

版本滞后仅在新版本尚未登记时允许通过；声明领先源码、新版本已登记却声明滞后仍失败。报告引用未归档在常规模式提示、严格模式失败；字节改写、无效版本提交和索引哈希错误均失败。问题关闭仍要求独立角色和一次确认记录。

## 正式问题

### DEV-031（中，product，归属维护者，open）

**模块树查询失败被当成内容相等。** `tools/identity.py:908` 比较两个 `git rev-parse` 返回值，Git 包装在失败时返回空字符串。两边都没有模块时，不会产生“模块树不同”问题。

- 证据：独立临时 Git 对象表均没有模块路径，查询均失败；仅保留共享输入并自洽重算的候选可通过 delivery 核验，交付签名使用临时密钥并由 Git 独立验证。
- 影响：身份工具可以认可缺少所声明模块的交付记录。正常受控构建会拒绝缺模块；本次未证明现有候选或交付缺模块。
- 建议：把不存在或非 tree 的模块对象作为查询失败处理，再比较有效树对象；同步 `docs/process/01-identity.md:119` 中残留的祖先硬要求。
- 频率：未知；置信度：已确认。
- 关闭条件：维护者修复后，Developer 在新冻结工具提交上复核缺模块被拒、有效同树无祖先关系被接受；KernelPatch 依赖变化继续允许。由独立于维护者的角色关闭。

### DEV-032（中低，product，归属维护者，open）

**历史报告缺提交时，当前字节被当成历史字节。** `tools/check_repository.py:889` 对任何缺少 commit 的版本都使用 current，不区分历史版本和当前待提交版本。

- 证据：基线与当前报告均已提交，当前内容是纯追加，登记的追加哈希正确。仅删除 versions 中旧版本的 commit，保留 append_only_baseline 的有效提交。常规检查产生 FAIL“第 2 段追加哈希与登记不符”，而不是历史缺提交的 WARN；严格模式依然失败。
- 原因：遍历旧版本时 prev 被提前设置为 current，遍历真正当前版本时 suffix 变为空，与实际追加段哈希不符。
- 影响：把元数据历史提交缺项误判成报告字节损坏；未发现严格模式放过损坏的报告。
- 建议：历史字节不可读取时走历史提交缺项分档，不能拿当前字节代替；保留严格失败。同步软硬分类说明。
- 频率：低频；置信度：已确认。
- 关闭条件：维护者修复后，Developer 在新冻结提交上复核历史缺提交常规 WARN／严格 FAIL，并复核真实原文改写、追加哈希错误仍 FAIL。

问题编号已检查未占用，问题载荷见同名 JSON；等待维护者登记与修复，本轮不关闭。
