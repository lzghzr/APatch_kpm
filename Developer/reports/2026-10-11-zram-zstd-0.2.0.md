Developer；2026-10-11。冻结源提交 `4f2a50487f9f06a8cbbd41108974ed440facb1a6`。本轮是实现方构建与离线自检，不是独立审计或实机结论；0.1.0 的审计、设备记录与风险接受保留，新字节需要重新绑定证据。身份三要素见 [交接清单](handoffs/zram-zstd-0.2.0-20261011.json) 与 [自检收据](data/2026-10-11-zram-zstd-0.2.0.json)。六种候选已通过统一事务内 candidate 档核验，交接清单尚待维护者导入 metadata。

## 适配范围与实现

本轮选择 4.4、仓库的 `kernel_mi8-4.9`（4.9.186-perf-g10af704）和 `kernel_mi9-4.14`（4.14.180-perf-gb24d113）。4.4 原始 Image SHA-256 为 `7633fbac5ce30b726a1acdbf57f730aa847a9510984a25bc23f9ddcdb0956e1c`；两份新目标的完整镜像／符号哈希和交叉依据见模块 `tools/references/`。4.9／4.14 的符号表复用 Developer 厂商符号恢复语料，重新核对镜像与符号哈希，未声称本轮独立提取。

上游 4.14 已包含 ZSTD 库，但 Crypto API 的 ZSTD 在 [4.18 Kconfig](https://github.com/torvalds/linux/blob/v4.18/crypto/Kconfig) 才提供；[4.17 Kconfig](https://github.com/torvalds/linux/blob/v4.17/crypto/Kconfig) 未提供它。因此本轮先补齐 Android 常见的 4.4、4.9、4.14；更高版本由实际 `crypto_has_alg()` 查询决定是否跳过，不按版本号填偏移或宣称所有厂商内核自带算法。

| 字段 | 4.4 | 4.9 | 4.14 |
| --- | --- | --- | --- |
| flags / name | 0x20 / 0x38 | 0x20 / 0x38 | 0x20 / 0x38 |
| driver_name | 0x78 | 0x78 | 0xb8 |
| compress / init | 0xc0 / 0x100 | 0xc0 / 0x100 | 0x140 / 0x180 |
| tfm ctx | 0x80 | 0x80 | 0x80 |

`zs_btf.c` 与 `zs_functions.c` 独立保存两路获取，`zs_offsets.c` 保存配置表、调度和公共检查。BTF 仅在接口或数据不可用时返回 `-ENODATA`；有效 BTF 的错误直接保留。名字数组从目标取得 64／128 字节宽度，配置表保留原五项顺序并追加 driver_name，第六项令本版静态表长为 12 字节。必要字段失败即停止初始化。

短锚点依次为 crypto_register_alg（8）、crypto_check_alg（16）、crypto_compress（8）、crypto_mod_get（8）与 lzo_init（16）。参考值来自另一入口：native lzo 数据对象、crypto_decompress、crypto_create_tfm 成功块、__crypto_alg_lookup 和 lzo_compress。4.14 的 cra_init 位于 create_tfm 第一处 RET 后，本轮改用 mod_get 的 module 连续片段，保持短窗口。

ZSTD 使用官方 [v1.3.1](https://github.com/facebook/zstd/tree/v1.3.1/contrib/linux-kernel) 的 `contrib/linux-kernel`，Git 子模块固定到 `aecf3b479c45affa9fd8ead068e9160253a8ec5c`。原 18 份文件与固定源字节一致，兼容头移至模块 `compat/`。构建检查提交、干净状态与来源哈希，在独立输出目录生成三处地址运算修补。KPM 自行编译 codec，宿主 libzstd 只用于独立互解。

加载事件保持 `post-kernel-init`；原生算法存在时以 `-EEXIST` 跳过。注册后仍需常驻，不改变已初始化的 zram。ctl0 使用 rek 彩蛋 `_(._.)_`，忽略输入参数并核对含 NUL 的八字节输出与实际复制长度。

## 构建与自检

新空目录保留所有失败探索与事务现场，未覆盖原 artifacts／MANIFEST。统一事务使用：

```sh
python3 tools/build_candidate.py zram_zstd --toolchain ndk26.3.11579264 \
  --target 'all debug legacy legacy_debug' --env ANDROID_NDK="$ANDROID_NDK" \
  --env LAYOUT_DIR=../local/zram-layouts-01 --extra-input patch_offsets.py \
  --handoff Developer/reports/handoffs/zram-zstd-0.2.0-20261011.json
```

Makefile 将生成源码、布局 JSON 和 legacy 转换输入／回执放在独立 LAYOUT_DIR；legacy 编译与 `patch_offsets.py legacy-kp` 在同一事务内。输入集合、配方捕获和转换工具指纹均由事务核对。工具链为 NDK 26.3.11579264，SDK 为 `b51197aaba8f2272dd8a3e30c85698a29aa928c9`。用户明确授权了两处共享工具及通用开发技能更新，`.gitmodules` 只增加本模块子模块声明。

- 三个实际目标的生产 C 推导逐字段匹配参考；ASan／UBSan 自检各处理 256 个 4096 字节页面，并与独立 libzstd 双向互解；ctl0 边界、短复制、部分分配与串行清理通过。
- 合成 BTF 检查 64／128 字节数组、无数据回退、原生错误保留、必要类型缺失和不符布局。合成数据仅验证契约，不充当三个目标的 BTF 证明。
- 寄存器覆盖、pair 第二目标、访存写回、短锚点缺失、RET／B 后的相邻函数模式均加入拒绝检查。
- 六份 ELF 的导入与当前 SDK 导出一致；可执行节反汇编未观察到 FP／SIMD／SVE 或 x18 寄存器操作数。旧 KP 的其余导出仍需目标设备复核。
- 三目标、两种静态形态的补丁只改变 12 字节配置表；回补 -1 后原始字节完全恢复。普通基线模板仍全为 -1，使用前需填写目标数据。
- 真实 legacy 两份输入的 13 个直接 CALL26 均保留到本地转接；原名指针缺失时追加对象导入。增加已有原名导入夹具后，既有 Oracle helper 核对指针 ADRP／LDR／BR、重定位与原节保留。无 suffix、短坏 ELF、多 symtab、重复转接均以 ValueError 拒绝。
- 共享工具原有自检 25/25、artifact gate 原有测试 37/37；新增冻结 gitlink／命名正反检查通过。六种产物及两份基线 JSON 的独立目录产物门禁通过。

ctl0 的原响应断言按用户明确要求更新为彩蛋，同时保留复制与边界拒绝；0.1.0 的五项缺省 4.4 偏移断言保留，增加第六项和其它目标的绑定哈希参考。该协议调整及新增布局参考交 Auditor 独立复核。

`Developer/tools/test_legacy_kp.py` 原 SHA-256 `cbe4e29e60fe010bfbe2dcbd988cdeffe7b6377dfa94c85caa2991aba2ea022a` 保持不变，本轮重新运行仍在要求纯改名的符号断言处 FAIL；记录在本轮收据。历史 DEV-028 的 Oracle 复核边界保留，本轮不弱化断言、不关闭该问题。现有 adapter／import helper 也未修改。

MNT-015 的 Developer 实现响应：本轮提供带内嵌 `kp_compat=legacy` 的普通／debug 候选，以及转换契约收据。维护者导入后按新 instance_id／SHA-256 请求复测，本轮不关闭 MNT-015，也不继承旧派生件的设备结论。
