# 真机异常升级流程（死机 / 卡死 / 无响应）

前提：**真机环境不可靠**。KPM 直接改内核内存与指令流，错偏移、上下文错误、生命周期错误都会表现为死机、软重启、卡死或随机 panic。
Tester 的目标不是「把设备救回来」，而是**保住现场证据**并**尽快把问题交给维护者**。

## 1. 判定

出现以下任一情况即进入本流程：

| 现象 | 判定阈值 |
| --- | --- |
| `adb` 命令无响应 | 单条命令被**脚本自带看门狗**杀掉；首次连接检查可做一次有界重查，加载开始后的首次超时即升级 |
| 设备重启 | 加载后 `boot_id` 改变或 `uptime` 变小，或出现重启循环 |
| 内核崩溃 | `dmesg` / `console-ramoops` 出现 `Unable to handle kernel`、`BUG:`、`Kernel panic`、`Call trace`：**出现即升级**（不自动卸载、保现场）；**缺席不算通过**，只能记"未观察到" |
| 界面卡死 | 屏幕冻结、触摸无效、无开机动画但设备未关机 |
| 加载无返回 | `truncate <superkey> module load ...` 超过 `--timeout` 仍无返回（由看门狗终止） |
| 脚本退出码 **90** | 看门狗判定**设备无响应**（超时或被信号杀死，rc=124 或 ≥128） |
| 脚本退出码 **1** | **判据 FAIL**（含 KP 控制命令按状态返回非 0，例如"已加载/已卸载"）：这是实现/测试问题，**不是**设备无响应，不要按本流程处理 |
| 脚本退出码 **3** | 加载前检出 pstore 残留旧崩溃 → 停在加载前，先问维护者（C4） |

## 2. 立即停止（必须）

1. **停止一切重试**：不再加载同一个 `.kpm`，不再换变体重试，不再重复 `module load`。
2. **不自行改代码/改偏移**：「设备上试出来的偏移」不是证据，改完再试会把一次清晰的失败变成一串无法归因的失败。
3. **不做恢复性操作**：不刷机、不进 recovery、不清数据、不改 superkey、不卸载/重装 APatch。
4. **恢复动作与执行者**（退出码语义见 [02-roles.md](02-roles.md) C1.1）：
   - Tester **可以**先尝试一次 `adb reboot`（软件重启，已预先授权，见 [02-roles.md](02-roles.md) A2）：
     重启可能改变现场；先尽力采集可读证据并通知维护者，恢复结果写入回执。
     前置条件：已记录四项基线、基线 pstore 为空，并且仅为无响应类异常；若当前发现 pstore 非空或崩溃特征，保留现场交维护者裁决；
     只允许一次，之后仍无响应就停手升级，不得再试。
   - 软件通道不可用时，**长按电源键等物理动作由维护者执行**：Tester 用升级单的
     「需要维护者执行的物理动作」一栏发起（动作、原因、期望、风险），维护者执行后在「动作回执」回填
     （时间、动作、结果）。**Tester 不自行找人手、不反复插拔/重启。**
   - 无论哪种恢复方式，重启后第一件事都是采集崩溃日志（见第 3 步），并记录时间/动作/结果。

## 3. 采集证据（尽量全，采集不到就写明采不到）

```bash
bash Tester/tools/collect_evidence.sh --build-id <build_id> --out Tester/reports/escalations/
```

脚本会尽力收集（每项都带超时，失败不阻塞其它项）：

| 证据 | 来源 | 说明 |
| --- | --- | --- |
| 崩溃日志 | `/sys/fs/pstore/console-ramoops*`、`/proc/last_kmsg` | **最关键的证据**，重启后仍存在 |
| 内核日志尾部 | `adb shell dmesg \| tail -n 400` | 采集前不要 `dmesg -c` 清空 |
| 模块状态 | `truncate <superkey> module list` / `module info <name>` | 若 adb 可用 |
| 设备环境事实 | `uname -a`、`getprop ro.build.fingerprint`、`getprop ro.product.model` | 机型脱敏，序列号只存 sha256 前 8 位 |
| 回归时间线 | `uptime`、`/proc/stat` 的 `btime`、加载命令时间戳 | 用于判断是软重启还是卡死 |
| 最后一次成功的步骤 | 测试脚本日志 | 指明在哪个判据上失败 |

采集后**不要**清理现场：保持设备当前状态直到维护者决定下一步。

## 4. 写升级单并通知维护者

用 [../templates/escalation.md](../templates/escalation.md)，文件名 `Tester/reports/escalations/<run_id>.md`（`run_test.sh` 自动生成 `<日期>-<模块>-<产物基名>#<n>.md`），必须包含：

- **身份三要素**：完整 commit + instance_id + 产物 SHA-256（死机时最需要知道「跑的是哪一份字节」）。
- **运行身份与证据保留**：日志、报告和升级单共享唯一 run_id。分配身份时检查 RUNDIR 与 ESCDIR 的全部同名输出，设备操作前排他保留路径；后续写入拒绝覆盖。更换运行目录或仅保留了旧升级单时，同样保护旧证据。
- 复现步骤：从预检到死机的完整顺序、用的哪个变体、是否首次加载、加载前设备状态。
- 现象与时间戳、脚本退出码、证据文件清单（相对路径）。
- 已尝试与未尝试的动作（明确写出「未做恢复性操作」）。
- **请求事项**：需要维护者裁决什么（是否继续测、是否需要 Developer 介入、设备是否送修/重刷）。

通知渠道（任选并留痕）：会话中直接 @维护者（附升级单相对路径）、仓库 issue（标题带 `<module> <build_id> 死机`）。**不要**把设备序列号、superkey、抓包原文贴进 issue。

## 5. 维护者响应（流程侧）

维护者收到后：

1. 按身份三要素确认跑的是哪份产物；在 `metadata/modules/<module>.json` 的 `issues` 里开一条 `TST-xxx`（严重度默认**高**，除非证据表明与模块无关）。
2. 指派归属：实现缺陷 → Developer；测试脚本缺陷 → Tester；平台/设备问题 → 记录为环境事实。
3. 裁决测试是否继续（同一 build 允许再测的前提：问题单已定位到具体判据且维护者书面同意，且 Device 已恢复稳定运行）。
4. 修复后产生**新 Build ID**；重新走预检，且新候选默认从「最保守的用例」开始（单个变体、单个判据）。

## 6. 什么时候可以继续测

同时满足才继续：

- [ ] 升级单已提交，问题单已开且归属明确。
- [ ] 设备已恢复稳定（连续 10 分钟无重启、`adb` 正常、`dmesg` 无新增崩溃）。
- [ ] 维护者书面同意继续，并指定测试范围。
- [ ] 若换了候选：使用新的 Build ID，旧产物保留不覆盖。

## 7. 常见误判

- **把环境限制当缺陷**：设备本身不稳、USB 掉线、adb 版本不匹配导致的无响应，要写成环境事实。
- **把测试缺陷当实现缺陷**：superkey 错误、路径不存在、`truncate` 未安装导致的失败，是实现方之外的测试缺陷。
- **证据被自己毁掉**：进入流程前执行了 `dmesg -c`、重装模块、清 pstore，会让问题无法归因——这也是要写进实机报告的事实。
