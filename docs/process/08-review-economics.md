# 复核经济学：让独立性花在影响上

本文件规定**独立复核成本如何与影响成比例**。三方角色由**三个独立智能体**承担（各自上下文、职责与写入范围），
角色隔离是真实的：共享的只是同一台主机与同一个仓库。因此本文优化的是**往返耦合**，不是独立性本身。

## 起因：一轮真实数据的账

以 zram_zstd 0.1.0 一轮为例：

| 维度 | 数量 |
| --- | --- |
| 自研代码 | 567 行（模块 + 自检脚本 + Makefile） |
| 流程往返文本 | 1035 行（审计报告 239、复核报告 132、登记记录 392、请求 164、回执 108） |
| 元数据/文档改动 | 22 个文件、8829 行插入 |
| 提交 | 6 个，其中代码提交 2 个 |
| 问题单 | 4 张，其中**记录类 3 张**（报告措辞、引用标识笔误、回执计数） |

结论：成本不在"出错"，而在**每一条问题——无论影响大小——都走同一套多轮独立复核链**。

## 三个根因（已按实际证据修订）

1. **可机检的错误走了人工往返**：把 KernelPatch 写成 `b51197aba`（不可解析），触发一整轮单。
2. **引用早于入库**：报告未提交即被元数据引用，导致"字节身份不可核"，进而需要判定"整份哈希是否恒定"。
3. **关闭流程不随影响分级**：severity 分四档，关闭却一律要求独立复核者 + 关闭条件 + 多轮往复；
   更正还逐条发现、逐条发单，串行化放大往返。

> 说明：此处曾把"三角色同一主体扮演"列为根因之一，**该判断有误并已撤回**。角色由三个独立智能体承担，
> 独立性成立；对外表述按 `identity.json` 的 `role_separation` 口径，既不夸大为多主体持钥，也不贬低为同一主体。

## 规则

### R1 可机检的一律机器检（门禁，见 `tools/check_repository.py`）

| 判据 | 拦截什么 | 模式 |
| --- | --- | --- |
| `identity_tokens` | 结构化提交字段必须可解析（KernelPatch 字段在子模块对象库核验） | 失败即失败 |
| `report_versions` | 报告字节身份：原文基线不可改写、现行字节须以基线为前缀、每次追加登记版本、索引哈希须是已登记版本 | 失败即失败 |
| `report_versions_coverage` | 尚未纳入版本索引的历史模块记录 | 提示 |
| `referenced_reports_archived` | 被引用的报告须已入库且与工作树一致（"先入库再引用"） | 常规提示，验收/交付失败 |

原则：**同一个错误只允许出现一次**——每轮把新发现固化为判据或 `tools/selftest_tools.py` 夹具。

### R2 问题分类决定关闭成本

问题单新增 `class` 字段（`identity.json.conventions.issue_classes`）：

| 类别 | 范围 | 关闭路径 |
| --- | --- | --- |
| `product` | 代码、产物、安全、身份、构建事务 | **不变**：独立复核者 + 关闭条件 + 完整证据链 |
| `record` | 报告措辞、计数、索引、元数据文字 | owner **一次更正** + **一次独立确认**即关闭；同轮内批量处理；禁止多轮往复 |

`record` 类同样必须留痕：更正前后文字、哈希、确认记录（`reviews[]`，门禁校验已关闭的 `record` 单必须有一次确认）。
**低风险不等于可静默消失**——只是轮数为 1，不是 0。

### R3 更正批量窗口

每轮冻结/登记点后，统一收集所有待更正项为**一批**交对应角色，一次处理、一次复核。
禁止"发现一条发一条"：本轮 `MNT-013` → `MNT-014` → `DEV-030` 的串行发现就是反面样本。
批量窗口内允许"待更正清单"临时记录在维护者记录中，不要求逐条成单。

### R4 先入库，再引用

角色报告产出后**先落提交**（允许无签名检查点），再由 `metadata` 引用。被引用路径在验收/交付模式下必须
已入库且与工作树一致。这样"登记后被改写"从"人事后追查"变成"门禁当场红"。

### R5 报告版本索引取代"整份哈希恒定"

`report_versions[]` 记录 `原文基线（提交 blob）+ 只追加版本（整份哈希、追加段哈希、提交）`。
判据是**原文前缀不可改写 + 追加逐一登记**，不是整份哈希永不变——后者与"授权在同一报告内追加更正"自相矛盾。

### R6 增量复核（`incremental` 档）

复核范围可限定为：修复 diff + 受影响节区/判据 + 受影响的实例；其余沿用原报告并**显式声明"未重做"**。
适用于修复边界清晰、输入未变的轮次；边界不清或输入变化时仍走完整复核。

### R8 交接即提交（检查点提交）

每个角色在**自己拥有的路径**内的产出（报告、回执、交接清单、逐项数据）**一产出即做无签名检查点提交**：

```bash
git add <自己路径内的文件>
git commit --no-gpg-sign -m "checkpoint(<角色>): <产物>"
```

理由：未被提交的字节状态**等于不存在**——本轮 v1/v2/v3 三个版本之所以"永久不可核对"，就是它们只存在于工作树。
每步提交后，任何历史版本都可按提交复算，追加更正退化为"门禁提示 + 一行索引更新"，而不是一张问题单加多轮往返。

边界：只有无签名检查点；不得 `tag`/`push`、不得 `checkout/restore/reset/stash/clean`、不得提交他人拥有的文件；
交付级签名提交 D 与标签仍只由维护者产出（见 [02-roles.md](02-roles.md) 的「角色检查点提交」）。
检查点提交**不是签名**：它证明"某时存在这些字节"，不证明"由该角色撰写"。

配套门禁 `report_version_commits`：`report_versions[]` 中除「当前工作树这一版」（须标 `pending_commit`）外，
每个版本都必须引用提交；字节确实不可恢复的历史状态登记在 `unarchived_versions[]` 并写明原因。
常规模式提示，验收/交付模式失败。

### R9 不得为提速削弱的项

高风险项的独立复核、身份三要素绑定、"未覆盖不得写成通过"、产物不可覆盖、断言不得为过门禁而放宽。
省的是**记录类问题的仪式**，不是证据本身。

## 变更管理

本文与门禁判据的每次调整都要：写明理由（影响/成本证据）、附**正反回归**（`tools/selftest_tools.py` 夹具）、
在 `docs/records/` 留一条维护者记录，并说明新判据的覆盖范围（是否只施加于新记录）。

## R10 门禁预算（条目数与运行时间）

门禁是每轮都要跑的工具，条目数与耗时都属于受控资源：

1. **并入优先**：新增判据应并入既有条目（同一次遍历、同一条结果输出），不为同一批数据另开检查项。
2. **禁止逐项子进程**：git 对象读取用 `git cat-file --batch`；文件集合与脏状态用一次 `git ls-files -z` /
   `git status --porcelain -z`；同一提交的多次查询跨调用缓存。禁止「每个文件/每条记录起一个 git 进程」。
3. **改动留数**：每次门禁或身份工具改动，记录改前/改后的**条目数**与**运行时间**，并给出**判定一致性证据**
   ——用旧版本在同一仓库状态上跑一遍，比较失败/警告集合；只允许检查项合并或提速，不允许判定放宽。
4. **自检同步**：合并后每个原判据的正反例必须仍在 `tools/selftest_tools.py`（或 `selftest_artifact_gate.py`）中
   被覆盖；夹具随语义调整时必须写明哪些语义变化，不得静默改期望值。

参考实测（2026-10-11）：把四条报告类判据并为 `report_integrity`、结构化提交标识解析并入 `metadata_schema`、
三处逐文件取 blob 改为批量后，条目 21 → 17、`--strict` 耗时 132 s → 5.2 s，
旧版在同一状态上同样给出 0 失败 0 警告。

## R11 所有权分流与门禁摩擦台账

**判据 vs 机制**：
- **判据**（什么算合格：身份语义、命名契约、检查范围、阈值）＝维护者所有，改动需维护者落地。
- **机制**（让共享工具支持模块的合法结构变化：子模块迁移、产物元信息新字段、转换支持）＝**需要它的角色直接实现**，
  条件是 R10 的正反夹具 + 同轮提案记录 + 维护者逐字节复核采纳，且**不改任何判据**。
  这条是**标准授权**：角色不必逐次向用户/维护者 请示，用户也不必逐次批准。

**摩擦台账**：每次被门禁拦住，登记「谁被拦 / 哪一条 / 原因是自己没做完还是别人的待办 / 结构性修法」。
同类摩擦出现**两次**就必须改耦合（把"别人的待办"从不合格降为待办提示、或把机制从共享工具里解耦），
而不是继续逐次授权。见 [门禁判据与机制分流](../records/2026-10-11-gate-criteria.md)。

**结构性修法优先于放宽判据**：R9 的不可放宽清单（身份三要素、构建事务、独立关闭、产物不可覆盖、
真机死机不自救）永远不因"门禁太烦"而放宽；要动就动耦合。


## R12 新生成数据复用

报告与原始证据继续按现有 Git 身份和追加规则保存。新生成的多实例交接清单可在文件内按内容哈希复用相同输入、配方和构建事务；导入先完整展开，再执行原有指纹、实例、事务和产物核验。旧清单、已封存 MANIFEST 与既有构建记录不重写。生成器保留旧格式读取，引用缺失或哈希不符直接拒绝；自包含清单不依赖外部下载。见[生成数据复用记录](../records/2026-10-16-generated-data-reuse.md)。

普通轮次产物审计用完整 `--instance-id` 显式列出本轮实例，生成结果记录请求与实际范围；所选实例缺任何登记产物即失败。完整历史回归保留原范围，全局未登记产物和历史缺件扫描持续执行。多实例交接需要复用重复输入时显式使用 `--handoff <新清单> --shared-inputs`。机制采纳与独立确认见[收尾记录](../records/2026-10-16-report-generation-maintainer-adoption.md)。

## R13 每模块一份常驻记录，提交只引用既有路径（2026-10-25 立）

**问题**：一轮交付产生几十份短报告（2026-10-25 单日 45 份 / 45,611 行），同一事实在
报告、交接 JSON、元数据 note、交付文档里各写一遍。读者要读十几份才能拼出一轮的状态。

**规则**：

1. **每个模块维护一份常驻记录**：`docs/records/<模块>-record.md`（首次创建，之后只追加段落）。
   一轮结束写一节，标题为日期 + 主题（如 `## 2026-10-25 DEV-062 目标名越界校验`）。
2. **新轮次不新建报告文件**：Developer/Auditor/Tester 的结论以小节形式**追加进该记录**，
   分别标注角色与证据层级；需要长篇原始输出时放 `local/`（gitignore），记录内只留结论、判据计数与哈希。
3. **提交与元数据只引用既有路径**：`report_versions[].path` 指向这份常驻记录，
   靠 `versions[]` 追加登记字节版本；不因"这轮又做了一件事"新增第二个文件。
4. **记录单份上限 400 行**；超出时按模块拆分（如 `nomount-record.md` → `nomount-record-btf.md`），
   拆分同样只新建一次，之后继续追加。
5. **例外**：交付清单、验收记录、问题单、裁定/授权记录属**独立文档**，各自成文且不被合并进模块记录。

**判据**：一次交付周期内，同一模块新增的 `.md` 不超过 2 个（常驻记录 + 例外类文档各计）。
门禁暂不强制，由维护者在验收时核对并在验收记录里写明数量。

**理由**：报告的价值在结论与可核验的证据指针，不在篇幅与份数；把"每轮新增文件"换成"同一文件追加"，
读者与后续会话都只需读一处，同时保留完整的历史与哈希链。

## R14 脱敏与是否发布无关（2026-10-25 立）

**每一次交付都要脱敏，即使不发布、不推送、仅本机留档。**

- 交付物、`docs/records/` 记录、提交消息、文件名、Release 文本中的**本机绝对路径、设备序列号、
  密钥库口令、superkey 明文、抓包内容**一律清除；序列号换 `sha256(序列号)` 前 8 位指纹
  （口径见 `02-roles.md` A4/C8 与 `tester-handbook.md`）。
- 门禁 `public_file_hygiene` 只是兜底；它不覆盖的内容（如报告正文里的机型串、日志摘录）由维护者在验收时逐项检查并留痕。
- 已入库但含敏感项的文本：允许按"同路径脱敏重发 + 旧字节哈希留档"处理，旧哈希与替换处数记入交付记录；
  纯历史事实不允许借脱敏之名改动结论、判据或计数。
- 报告目录移出版本库（`.gitignore`）不豁免本条：本地留档同样按脱敏口径保存。
