# 问题单：格式、流转与关闭

## 问题单范围（避免审计资源被稀释）

| 情形 | 走哪里 |
| --- | --- |
| 未交接的普通编译错误、笔误、探索期反复试错 | **开发记录**：`Developer/reports/` 的报告与 `local/build_logs/` 日志即可，不必开正式单 |
| 安全相关（权限/生命周期/输入校验/信息泄露） | **正式问题单 + 独立复核** |
| 已交接候选（有 Build ID/instance、报告已引用）上的问题 | **正式问题单 + 独立复核** |
| 跨角色发现（Auditor/Tester 提出） | **正式问题单 + 独立复核**（由发现方复核关闭） |
| 回归失败（此前通过过，现在失败） | **正式问题单 + 独立复核**，无论看起来多小 |

判断原则：**一旦这个结论会被别角色引用、或会成为交付物的一部分，就必须进正式单**。

## 编号

`<角色前缀>-<三位序号>`，序号在整个仓库同一角色前缀下单调递增、不复用（模块记录共同占用编号）：

| 前缀 | 角色 |
| --- | --- |
| `DEV-` | Developer 自检发现 |
| `AUD-` | Auditor 独立审计发现 |
| `TST-` | Tester 实机发现 |
| `MNT-` | 维护者验收发现 |

示例：`AUD-001`、`TST-014`。

## 格式

```text
<角色前缀>-<序号>（严重度，归属角色）一句话结论
- 类别：product（代码/产物/安全/身份） | record（报告措辞、计数、索引、元数据文字）
- 证据：可复现命令与实测输出（哈希、计数、异常文本、代码位置）
- 影响：对用户/交付的实际后果
- 建议：可执行的最小修正
- 关闭条件：由谁、在哪个提交/实例、用什么证据关闭
- 频率：高频 | 中频 | 低频 | 未知（**与严重度分开记录**）
- 置信度：已确认 | 推断 | 未验证（证据强度，不参与定级）
- 状态：open | fixing | fixed(待复核) | closed | wontfix(需维护者批准)
```

模板：[../templates/issue-ticket.md](../templates/issue-ticket.md)

## 类别决定关闭成本

类别只影响**关闭路径**，不影响是否需要留痕或严重度：

| 类别 | 范围 | 关闭路径 |
| --- | --- | --- |
| `product` | 代码、产物、安全、身份、构建事务、判据工具行为 | 完整独立复核链（下文关闭规则不变） |
| `record` | 报告措辞、计数、索引、元数据文字 | owner **一次更正** + **一次独立确认**即关闭；同一轮内批量处理；禁止多轮往复 |

`record` 类同样必须留痕（更正前后文字、哈希），关闭时须有 `reviews[]` 一次确认记录（门禁校验）；
`closed_by != owner` 依然强制。轮数为 1，不是 0——**低风险不等于静默消失**。
批量窗口与门禁自动化见 [08-review-economics.md](08-review-economics.md)。

## 严重度

**严重度按影响定级**，出现频率与证据置信度分别记 `frequency` / `confidence`：

| 级别 | 判据（只看影响） |
| --- | --- |
| 高 | 可导致内核崩溃/死机/数据损坏/权限提升，或使已交付功能整体不可用 |
| 中 | 功能错误、状态错误、可被非特权方影响、跨版本兼容性缺口、身份追溯失效 |
| 中低 | 体验/性能/可维护性问题，或影响面很小的错误路径 |
| 低 | 文档、命名、注释、版本声明不同步 |

- **不要因为「不知道多久出现一次」而降级**：确认可致崩溃/提权的问题一律按影响定级为「高」，
  在 `frequency` 里写「未知」、在 `confidence` 里写「推断」即可。
- 反过来也不要夸大：只在特定内核/特定操作序列下触发的问题，`frequency` 写「低频」，
  严重度仍按影响（例如卸载路径崩溃 = 高）。
- **敢下判断，也要敢克制**：不要把环境限制写成产品缺陷，也不要把「能跑通」当「已验证」。

## 区分缺陷类型

- **实现缺陷**（归属 Developer）：产品代码/构建器的问题。
- **测试缺陷**（归属 Tester 或 Auditor）：测试脚本依赖私有接口、路径错误、权限不足导致失败；结论必须写清是哪一类。
- **环境事实**（无归属）：设备接收率低、SELinux 策略限制、语料缺镜像。环境事实不是产品缺陷，但可能限制结论。

## 关闭规则

1. **由独立于修复归属方的角色复核并关闭**：通常由发现方复核；发现方同时负责修复时，另指定角色。修复者只在自己的响应中声明 `fixed(待复核)`，维护者同步元数据。
2. 关闭必须写：`closed_by`、修复 commit、被验证的 `instance_id`、验证命令与输出。
3. **关闭者必须独立于归属方**（门禁强制 `closed_by != owner`）：`DEV-*`（Developer 自检发现）与
   `MNT-*`（维护者发现）都需要另一位角色复核——例如 Developer 自检的问题由 Auditor 或维护者复核关闭，
   维护者发现的问题交 Developer 复核。
   **字段语义**：`owner` 是**负责修复的归属角色**，`closed_by` 是**独立复核者**，两者必须不同
   （门禁强制）。若某条问题由发现方自己实现（例如 Auditor 修自己的工具、Developer 修自检问题），
   独立复核者就由**另一个角色**担任（通常维护者），`closure` 里要写明由谁复核。
   实现者本身可以记在 `implementer` 字段（可选，用于说明"谁写的代码"）。
4. `wontfix` 必须由维护者批准并在问题单里写明理由与风险接受范围。
5. 问题单一旦写入报告就**只追加**后续状态，不改写原结论。
6. 问题单编号与状态同时登记在 `metadata/modules/<module>.json` 的 `issues` 数组，门禁检查字段完整性、
   状态合法性、`frequency`/`confidence` 枚举与关闭者独立性。

## 周期性复核：已修未关（2026-10-24 增补）

**问题**：关闭条件依赖"独立角色复跑"，但没有任何机制安排这次复跑。代码持续演进，
修复可能早已随其它提交进入仓库，问题单却因没人回头验证而长期挂 open —— 状态失真，
既掩盖真实风险（分不清"还有 8 个问题"和"只剩 3 个"，也让人误判项目健康度）。

**规则**：

1. 维护者在**每轮收尾**（或开放问题单数量增长、或交付备料前）列出全部 open 单，
   逐条判断"后续提交是否已满足其关闭条件"；
2. 疑似已满足的，**派independent 复核**（执行者必须独立于修复归属方），**不得由维护者自行判关**；
3. 复核结论必须区分三态：**仍复现 / 已被后续改动消解 / 仍存在但性质变化**；
4. 判为"已消解"时**必须给出消解机制**——是哪个提交、哪个门控起的作用、以及可复核证据。
   **"反例跑一遍不报了"不等于"修好了"**，可能只是反例本身失效；
5. 消解机制的归因若与已撤下的反例有关，须按 `docs/records/2026-10-24-counterexample-retraction.md`
   的口径说明关联（区分"撤下假证据"与"否定真结论"）。

**实例（本规则的直接来源）**：`DEV-047`/`DEV-048`/`DEV-049` 于 2026-10-20 登记，
其修复其实早已分别由 `86f258a`（互斥门控、错误码透传）与 `95f5f2e`（`list_lru_count_node == 64` 物理门控）
落地，直到 2026-10-24 主动派复核才关闭 —— 中间数轮交付都带着三条失真状态。
