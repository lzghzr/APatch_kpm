# 反模式

以下做法在本仓库一律视为返工理由。

## 用自检冒充结论

- 用 Developer 的构建断言、`kernel_img/offset_harness` 回归、模块 `logkm` 输出当审计结论。
  harness 是 Developer 自己移植的，与设备上的 C 代码同源；它能证明「移植一致」，不能证明「推导正确」。
- 用「我这边能加载、日志正常」当实机结论。没有判据、计数与环境事实的观察不是结论。
- 把「能跑通」当「已验证」。

## 破坏身份追溯

- 重写或"更新"已登记的构建记录（改 commit/时间/产物路径）：只能追加新实例。
- 覆盖已归档的产物或 `MANIFEST.json`；用同一 `build_id` 装两套不同字节。
- 用当前工作树核验历史构建（源码一改旧候选就"不一致"）：应按记录绑定的 `source_commit` 核验。
- 只按单一字节表示核验源码指纹（`core.autocrlf` 之类会误判）：应记录工作树与提交 blob 两种表示。
- **只检查字段存在就宣称"身份已核验"**：指纹必须能按记录输入**重算**，参数必须真的捕获过，脏树不能当候选。
- 用同一个 Build ID 装不同编译参数/依赖的产物（应自然得到新 Build ID；同 ID 不同指纹会被工具拒绝）。
- 只清 `.kpm` 就以为构建目录干净（旧 `.o` 会被 `make` 直接复用；应连中间产物一起移走并 `-B` 强制重建）。
- 把 `make -n` 的非零输出当参数指纹（返回码非 0 时必须判定捕获失败）。
- 验收记录与实例指纹不一致却只当警告放行（门禁必须失败）。
- 把 `delivery_commit` 写回构建记录（构建记录只追加；交付信息应追加到 `deliveries[]`）。
- 清理构建目录时用通配符把源码一起清掉（`*.s` 之类既可能是产物也可能是源码；要保护构建输入与已跟踪文件）。
- 先构建再回想用了什么参数；或拿模块目录里现成的 `.kpm` 当本次构建结果
  （用 `tools/build_candidate.py`：输入快照 → 移走旧产物 → 构建 → 复核输入未变）。

## 身份缺失或含糊

- 报告用「最新版」「当前代码」指代对象，不写 commit 与哈希。
- 先提交再断言身份；或产物已重建覆盖后再补哈希。
- 签名不可用时用未签名提交交付，事后补签（应等签名可验证再交付）。

## 跨角色越界

- Auditor/Tester 直接改模块源码「顺手修一下」。
- 修复者自己关闭问题单。
- 维护者改写角色报告里的结论（只能在追加的「维护者记录」里写明）。

## 偏移与兼容性

- 按内核版本号分支决定偏移或逻辑（`LINUX_VERSION_CODE`、`utsrelease` 比较）。
- 推导失败就猜一个偏移硬上，或静默取多个候选中「看起来对」的那个。
- 只在一台设备/一个内核上验证就宣布跨版本支持。

## 真机试错

- 死机后自行反复重启、反复加载同一个 `.kpm`、现场改偏移再试（正确动作见 [07-escalation-device.md](07-escalation-device.md)）。
- 把环境限制（SELinux 拦截、接收率低、抓包不全）写成产品缺陷。
- 把设备序列号、superkey、抓包原文写进公开报告。

## 门禁与流程

- 为了让检查通过而放宽断言、跳过用例、缩小检查范围。
- 同一个 Build ID 对应多套产物字节；用同一输出目录重建覆盖旧产物。
- 在公开文件里写入本机绝对路径、设备标识、密钥。
- 给不该进 CI 的模块目录漏加 `archive`（CI 会继续构建它），或反过来给文档/工具目录加 `archive`（多余：没有 Makefile 的目录本就跳过）。

## 测试基准与反向过拟合

- **篡改基准测试**：当测试失败时，私自修改、注释或删除已有断言来使测试通过（违反 [respect-the-oracle](../../.agents/skills/respect-the-oracle/SKILL.md) 的 Oracle 不可变原则）。
- **反向架构污染**：为了迁就宿主单测/Mock 桩或脱离真实内核事实的断言，在生产内核代码中引入冗余局部变量、伪回滚暂存或扭曲正常控制流。
- **隐蔽削弱断言**：将断言删除/放宽与业务改动混在同一提交中，不单独声明且不经 Auditor 独立复核。
- **虚假置信度**：将宿主机合成测试（Tier-3）的通过率当作真实内核稳定性与安全性的替代结论。
