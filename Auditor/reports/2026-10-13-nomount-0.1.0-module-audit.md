### 3.4 目标配置偏移来源与推导链审查

审查 `nomount/configs/boot_los23.2.json` 中的 38 项配置：
- **目标环境事实**：内核 `4.19.325-cip134-st18-perf-g7fc8455b2fa8`，镜像未启用 BTF（`CONFIG_DEBUG_INFO_BTF=n`），启用了 `CONFIG_CFI_CLANG=y`；因此必须采用静态预推导 baselines 模式；

  - 核心结构偏移（`file_inode_ops=32`, `file_mapping=240`, `inode_superblock=40`, `inode_number=64`, `dentry_ops=96`）经由 `vfs_llseek`、`iterate_dir`、`generic_fillattr`、`d_set_d_op` 等短函数反汇编数据流交叉推导并与匹配内核源码（`7fc8455b...`）声明核对一致；
  - 互斥锁 `mutex_size=32`, `mutex_no_lockdep=1`：核对目标内核配置未启用 `CONFIG_DEBUG_MUTEXES` 或 `CONFIG_LOCKDEP`，原生 `struct mutex` 包含 `owner` (8B) + `wait_lock` (16B) + `osq` (8B) = 32 字节，无 `dep_map` 结构；

### 3.5 CFI hook（`__cfi_slowpath`）机制审查

针对目标内核启用的 Clang CFI：
1. **目标符号核实**：Auditor 提取 `boot_los23.2.img` 的内核 Image，符号表检索确认存在全局导出函数 `__cfi_slowpath`（地址 `0x3dd20c`），且不存在 `__cfi_slowpath_diag`；
2. **KernelPatch CFI 穿透逻辑**：
   - 走查 `KernelPatch/kernel/patch/common/secpass.c` 中的 `bypass_kcfi()`：在检测到 `__cfi_slowpath` 存在时，通过 `replace__cfi_slowpath` 截获检查；
   - 截获函数调用 `should_cfi_pass((unsigned long)ptr)`，当指针落在 KernelPatch 的模块可执行内存区域（`is_exec_allocated`）时直接跳过 CFI 中断返回，从而保护模块注册的原生 VFS 回调；
3. **前置条件必要性确认**：
   - KernelPatch 的 `secpass.c` 不向 KPM 导出 `cfi_bypass` 的运行时状态；
   - 若加载阶段 CFI hook 因地址错位或内核抢占未能生效，后续 VFS 调用 KPM 回调将立即触发 CFI Panic；
   - **Auditor 确认**：Developer 与维护者制定的前置条件——「Tester 必须在加载前绑定实际 KP/boot 身份，并核实 dmesg 日志确认 `hook __cfi_slowpath_diag: ..., error: 0` 命中后方可嵌入加载 NoMount」——是**必要且完全合理的技术约束**。

## 4. 卸载保护与 RA-002 前提独立确认

维护者在轮次请求中要求 Auditor 独立确认 `RA-002`（卸载致 UAF，高）的前提是否成立。

### 4.1 独立代码走查事实

1. **模块退出回调行为**：
   走查 `nomount/nomount.c:54-58`：
   ```c
   static long nomount_exit(void* reserved) {
     if (nm_initialized)
       pr_err("NoMount: do not unload; native keyring and VFS may retain callbacks\n");
     return 0;
   }
   ```
   模块在 `exit` 回调中**未执行任何回调注销或操作表还原**（`key_type`、已发布的 inode/dentry 代理表均驻留），仅输出日志。
2. **KernelPatch 模块卸载机制**：
   走查 `KernelPatch/kernel/patch/module/module.c:540-547`：
   ```c
   list_del(&mod->list);
   rc = (*mod->exit)(reserved);

   if (mod->args) kvfree(mod->args);
   if (mod->ctl_args) kvfree(mod->ctl_args);

   kp_free_exec(mod->start);
   kvfree(mod);
   ```
   **关键事实**：KernelPatch 在调用 `(*mod->exit)(reserved)` 后，**完全不检查返回值 `rc`**，随后无条件调用 `kp_free_exec(mod->start)` 释放模块的所有可执行代码内存！

### 4.2 独立技术结论与 RA-002 裁决

- **后果推演**：即使模块实现尝试返回 `-EBUSY`，加载器仍会强制释放模块内存。内存释放后，内核中的 `key_type` 链表、VFS superblock/inode 操作表指针仍指向已释放区域。任何后续访问（如应用打开文件、遍历目录或查询密钥）将立即触发 Use-After-Free，导致整机崩溃（Panic）或静默内存破坏；
- **裁决结论**：
  1. **RA-002 的风险定级与前提完全成立**：卸载必然触发 UAF Panic，影响定级为「高」；
  2. **唯一安全策略**：在 KernelPatch 提供卸载返回值阻断或模块实现完整安全注销前，**严禁卸载与动态重载**；模块生命周期必须严格限定为「`post-kernel-init` 开机嵌入加载，常驻运行直至重启」；
  3. **建议维护者**：正式将 Auditor 的独立确认事实（代码引用 `module.c:540-547` 与 `nomount.c:54-58`）记入 `RA-002.evidence`。

### 9.1 原判据缺陷分析与 SDK 源码走查澄清

在原报告 §3.5 第 3 条中，Auditor 确认了 Developer 与维护者制定的前置条件，要求 Tester 在加载前核实 dmesg 出现 `hook __cfi_slowpath_diag: ..., error: 0`。经 Developer 指出并经 Auditor 独立重新走查冻结 KernelPatch SDK（`KernelPatch/kernel/patch/common/secpass.c:75-105`），确认原判据存在如下与实际代码分支行为不符之处：

1. **成功分支不输出该日志**：
   走查 `KernelPatch/kernel/patch/common/secpass.c:86-94`：
   ```c
   if (__cfi_slowpath_addr) {
       hook_err_t err =
           hook((void *)__cfi_slowpath_addr, (void *)replace__cfi_slowpath, (void **)&backup__cfi_slowpath);
       if (err) {
           log_boot("hook __cfi_slowpath_diag: %llx, error: %d\n", __cfi_slowpath_addr, err);
           rc = err;
           goto out;
       }
   }
   ```
   **事实澄清**：第 90 行的 `log_boot("hook __cfi_slowpath_diag: %llx, error: %d\n", ...)` 语句**严格位于 `if (err)` 分支内部**。当 `hook()` 挂接成功时，`err == 0`，该 `if` 条件为假，此行日志**根本不会被输出**！原判据要求捕获 `error: 0` 在技术上是不可能产生的。
2. **日志标签硬编码与符号混淆**：
   `secpass.c` 中的日志格式串硬编码为 `"hook __cfi_slowpath_diag: ..."` 以及 `"__cfi_slowpath_diag resolved at runtime: ..."`。但在 `secpass.c:76-85` 中，`__cfi_slowpath_addr` 优先从 `patch_config` 或 `kallsyms_lookup_name` 匹配 `__cfi_slowpath_diag`，若不存在则回退匹配 `__cfi_slowpath`。当实际解析到的是 `__cfi_slowpath` 时，输出的日志标签依然写着 `__cfi_slowpath_diag`。因此，不能单纯凭借日志文本中的标签名称推断实际命中的内核符号。
3. **汇总返回值不能单独证明挂接**：
   在 `secpass.c:96-105` 中，若目标内核既无 `report_cfi_failure` 也无 `__cfi_slowpath`（例如未开启 CFI 的低版本内核或未配置 patch_config 且 runtime 未找到），虽然会打印告警日志，但函数末尾 `return rc;` 依然返回 `0`，调用方打印 `bypass_kcfi done: 0`。因此，单独一条 `bypass_kcfi done: 0` 不能作为 slowpath 已成功挂接的充分证据。

### 9.2 CFI 证据链的四阶段证明范围划分

为彻底理清 CFI 防护穿透的证明边界，消除将不同层次证据混为一谈的问题，Auditor 将证据链明确划分为相互独立、层次递进的四个阶段：

| 阶段 | 证明范围（能证明什么） | 证明边界与局限（不能证明什么） | 可接受的核验依据 / 判据 |
| --- | --- | --- | --- |
| **阶段一：源码与内核配置分析** | 1. 目标内核开启了 Clang CFI（`CONFIG_CFI_CLANG=y`）；<br>2. KernelPatch 的 `secpass.c` 具备 CFI 穿透跳板设计（`replace__cfi_slowpath` 通过 `should_cfi_pass` 放行 KPM 执行内存）。 | 不能证明目标内核实际存在有效符号，不能证明地址正确，不能证明加载时 hook 执行成功。 | 目标内核 `.config` 声明、KernelPatch 上游 `secpass.c` 源码走查。 |
| **阶段二：符号地址解析** | 1. 目标内核镜像符号表中确实包含可作为挂接锚点的符号（如 `__cfi_slowpath` 或 `__cfi_slowpath_diag`）；<br>2. 获取其确切的静态偏移及运行期 KASLR 基址。 | 只证明内核具备被 hook 的基础锚点；不证明 KernelPatch 加载器找到了该符号，更不证明 hook 已经执行。 | 内核符号表解包提取（如 kallsyms / System.map）、ELF 符号段解析、运行时 kallsyms 查验。 |
| **阶段三：挂接成功（加载前条件）** | 1. KernelPatch 在初始化阶段成功获取了有效的 slowpath 地址；<br>2. `hook()` 执行成功（`err == 0`），目标指令跳转已被改写为 `replace__cfi_slowpath`。 | 证明 hook 已建立；但尚未证明当业务模块回调被内核间接调用时，`should_cfi_pass` 是否能正确匹配和放行。 | **必须满足（否定条件）**：<br>- dmesg / log_boot 中**无** `hook __cfi_slowpath_diag: ..., error: <非0>`；<br>- **无** `no symbol for pass kcfi` 告警；<br>**肯定条件（以下至少具备一项）**：<br>a. 若走运行时回退（runtime fallback）：dmesg 记录 `__cfi_slowpath_diag resolved at runtime: <有效地址>`，且随后 `bypass_kcfi done: 0`；<br>b. 若走启动预设（`patch_config`）：预设配置内包含有效的符号偏移，且 `bypass_kcfi done: 0`；<br>c. KernelPatch 运行时 hook 表查验：目标符号地址处于已生效 hook 列表中。 |
| **阶段四：真实 VFS 调用实测** | 内核 VFS 子系统通过函数指针间接调用 NoMount 注册的文件系统与 Keyring 回调（如 `read_iter`, `open`, `iterate_dir`, `lookup` 等）时，未触发 CFI 异常（无 CFI Trap / Oops / Panic），能够完成实际数据读写与目录枚举。 | 证明模块回调已实际被内核调用且穿透了 CFI 检查；但该证据属于事后端到端结果，不能反向替代或豁免加载前的阶段三前置条件检查。 | 真实设备环境下的 APK/文件读取实测、目录遍历实测、操作期间 dmesg 无 CFI 违规 Panic 日志、系统正常存活。 |
