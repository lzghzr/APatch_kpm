## 4. 6.1 定向目录 Actor ABI 审查（0.4.0 引入特性）

### 4.1 内核演进背景

在 Linux 6.1 内核中（上游补丁 `9081e3a6` "fs: introduce bool filldir_t / actor_t"），VFS 层将 `dir_context.actor` 回调函数的返回值由传统 `int`（返回 0 代表成功/继续，非 0 代表终止）修改为 `_Bool`（返回 `true` 代表继续，`false` 代表缓冲区满/终止）。
若在 6.1 内核上沿用传统 `int` 规范返回 `0`，内核 VFS 迭代器会将其隐式解释为布尔值 `false`，导致目录遍历在吐出第一个条目后即刻异常终止。

### 4.2 偏移表与实现审查

1. **偏移表扩展**：
   - 结构体偏移表从 45 项扩展为 46 项，总字节数由 90 字节增加到 92 字节；
   - 末项字段定义为 `int16_t dir_actor_abi`：
     - `0`：标准 `int` 返回值（适用于 <= 5.15 内核，返回 0 继续）；
     - `1`：布尔 `_Bool` 返回值（适用于 >= 6.1 内核，返回 true 继续）；
     - 默认初始化为 `-1`。
2. **严密门禁校验**：
   在 `nomount/nm_offsets.c` 中：
   ```c
   if (offsets->dir_actor_abi < 0) return -ENOENT;
   if (offsets->dir_actor_abi > 1) return -EOPNOTSUPP;
   ```
   禁止任何未推导猜想或非法取值，若未确认 ABI 严禁加载。
3. **回调分流**：
   在 `nomount/nm_directory.c` 与 `nm_backing_directory.c` 中：
   - 当 `dir_actor_abi == 1` 时，将 `context.actor_bool` 绑定到 `nm_directory_filter_bool`：
     ```c
     static bool nm_directory_filter_bool(struct nm_dir_context* context, const char* name, int length,
                                          int64_t offset, u64 number, unsigned int type) {
       return nm_directory_filter(context, name, length, offset, number, type) == 0;
     }
     ```
   - 语义转换清晰无状态残留，完美契合 6.1 内核布尔契约。
4. **BTF 动态探测**：
   在 `nomount/nm_btf.c` 中，动态解析 `dir_context.actor` 函数指针的返回类型 BTF 节点，依据其类型尺寸（1 字节 bool vs 4 字节 int）自动配置 `dir_actor_abi`，无需硬编码版本号。

## 5. 未移植上游重构的独立风险评估

上游提交 `1ded61d` 到 `7046c7a` (v2.1.1) 包含 25 个提交。其中用户态及 WebUI 变更已随配套 ZIP 同步，内核 LKM 的部分重构本轮未移植进 KPM。Auditor 针对以下 6 项未移植重构开展独立安全与正确性评估：

### 5.1 规则内联存储 (`d5955a2` "pack rule strings into the rule array")
- **上游改动动因**：上游 LKM 此前对每条规则的虚拟路径和真实路径分别做 `kmalloc`，长期频繁增删规则会导致小内存碎片。该提交将字符串字符紧凑打包进规则数组尾部。
- **KPM 现状评估**：KPM 采用常驻内存模型（`lifetime=reboot`），规则在启动加载期一次性完成拓扑建树与节点分配，不存在频繁的动态规则增删。KPM 自建的内存分配与生命周期追踪安全严密，无内存泄露。
- **风险判定**：**无安全风险**。属于上游 LKM 自身的内存布局微优化，不构成缺陷修复。

### 5.2 虚拟 Inode 与规则解耦 (`8005194` "decouple virtual inodes from rules")
- **上游改动动因**：上游 LKM 允许用户态随时删除规则。如果用户态删除了规则，而 VFS 缓存中仍有虚拟 Inode 存活且持有该规则的裸指针，会造成悬挂野指针解引用（UAF）。
- **KPM 现状评估**：KPM 架构严格受 **RA-002** 约束，不支持运行期动态删除规则或卸载模块。并且 KPM 自身的 `nm_inode.c` 在合成虚拟 Inode 时已将属性完整复制到代理节点中，未依赖临时的易失性规则指针。
- **风险判定**：**无安全风险**。该提交防御的是 KPM 根本未开放的动态规则注销场景。

### 5.3 RCU 规则退役与整批 ADD 锁重构 (`1f35f82`)
- **上游改动动因**：上游 LKM 每次添加一条规则都反复获取/释放全局互斥锁，并在规则数组替换时调用可能引起调度的同步原语。该提交将加锁外提至批处理外层，并改用 `call_rcu` 异步释放旧数组。
- **KPM 现状评估**：KPM 的控制接口 `nomount_ctl0`（`nm_control.c`）在接收到 keyring 载荷时，本来就是一次性获取互斥锁处理整批规则；在替换规则指针时使用 `smp_store_release` 配合 RCU 读保护。由于 KPM 需兼顾 4.4 等低版本内核，避免引入跨版本 ABI 脆弱的 `call_rcu` 内核工作队列机制符合嵌入式安全原则。
- **风险判定**：**无安全风险**。KPM 现行锁策略本就具备批处理特性，且无多线程竞态。

### 5.4 256-bit UID Bloom 预过滤器 (`27d4f0e`, `043ea66`, `6319390`)
- **上游改动动因**：上游为加快白名单/排除 UID 的匹配速度，引入了 256-bit Bloom 过滤器；但后续连续两个提交（`043ea66` 修复小集合跳过逻辑、`6319390` 修复哈希冗余计算）表明该特性引入初期存在逻辑瑕疵。
- **KPM 现状评估**：KPM 的排除 UID 集合通常极小（仅数个系统服务或特定隔离 UID），KPM 直接遍历有序 UID 数组的时间复杂度仅为极低常数级，无哈希碰撞假阳性风险，无逻辑膨胀。
- **风险判定**：**无安全风险**。避免接入处于演进波动期的 Bloom 代码有助于维持 KPM 稳定。

### 5.5 路径查找与目录迭代热路径微调 (`fe6a2fa`, `516de9d`, `64478a3`, `fcaa6c4`)
- **上游改动动因**：微调二分查找外部 entries 解析、跳过 no-op 下的 dentry 锁、消除冗余目录缓存剪枝等。
- **KPM 现状评估**：KPM 的 VFS 挂载点拦截与目录视图合并（`nm_directory.c`）采用静态函数指针和紧凑代理表，未采用上游那套运行期重写 dentry 操作表的特定逻辑。
- **风险判定**：**无安全风险**。

### 5.6 评估结论
经逐提交审查，**上游 v2.1.1 的上述未移植重构中不存在任何必须随本轮发布的安全性或正确性 Bugfix**（无 CVE、无缓冲区溢出修复、无内核崩溃漏洞修补）。KPM 0.4.1 维持现有架构是严谨、稳健且符合长期安全预期的合理技术决策。
