## 2. 根因分析与代码分支走查

Auditor 独立走查冻结编译平台 SDK `b51197aaba8f2272dd8a3e30c85698a29aa928c9`（0.13.9）中的 [`KernelPatch/kernel/patch/common/secpass.c:75-105`](../../../KernelPatch/kernel/patch/common/secpass.c#L75-L105)：

```c
    // todo: direct modify cfi_shadow, __cfi_check?
    unsigned long __cfi_slowpath_addr = patch_config->__cfi_slowpath_diag;
    if (!__cfi_slowpath_addr) {
        __cfi_slowpath_addr = patch_config->__cfi_slowpath;
    }
    if (!__cfi_slowpath_addr && kallsyms_lookup_name) {
        __cfi_slowpath_addr = kallsyms_lookup_name("__cfi_slowpath_diag");
        if (!__cfi_slowpath_addr) __cfi_slowpath_addr = kallsyms_lookup_name("__cfi_slowpath");
        if (__cfi_slowpath_addr)
            log_boot("__cfi_slowpath_diag resolved at runtime: %llx\n", __cfi_slowpath_addr);
    }
    if (__cfi_slowpath_addr) {
        hook_err_t err =
            hook((void *)__cfi_slowpath_addr, (void *)replace__cfi_slowpath, (void **)&backup__cfi_slowpath);
        if (err) {
            log_boot("hook __cfi_slowpath_diag: %llx, error: %d\n", __cfi_slowpath_addr, err);
            rc = err;
            goto out;
        }
    }

    if (!report_cfi_failure_addr && !__cfi_slowpath_addr) {
        // not error on kernels without CFI (<= 5.4); fatal hazard on CFI kernels
        log_boot("no symbol for pass kcfi (preset and runtime kallsyms both empty)\n");
        log_boot("if CONFIG_CFI_CLANG is enabled (Android 13+ GKI common), every kCFI mismatch on KP memory will panic -> random reboots\n");
    }
    cfi_bypass = 1;

out:
    return rc;
```

走查事实确认：
1. **成功分支无错误日志输出**：第 90 行的 `log_boot("hook __cfi_slowpath_diag: %llx, error: %d\n", ...)` 位于 `if (err)` 错误处理块内。当 `hook()` 成功注册时返回值为 0（`err == 0`），该分支不会进入，因此正常成功的执行路径**绝不会输出包含 `error: 0` 的该日志**；
2. **日志标签硬编码与符号回退**：日志格式串硬编码为 `"__cfi_slowpath_diag"`。在代码中，若 `__cfi_slowpath_diag` 为空，会回退到 `__cfi_slowpath`。但无论匹配到哪个符号，第 84 行与第 90 行的打印标签均固定显示为 `__cfi_slowpath_diag`，不能凭借该标签断定具体命中了哪个符号；
3. **汇总返回值存在误导性**：若内核符号未能解析且启动预设未配置，代码会打印告警（行 98-99），但函数正常流转至末尾时 `rc` 依然保持初始值 0，调用方据此输出 `bypass_kcfi done: 0`。因此仅凭 `bypass_kcfi done: 0` 单一日志行无法证明 slowpath 已被实际挂接。

原审计报告 §3.5 第 3 条中关于要求 Tester 核实 `hook __cfi_slowpath_diag: ..., error: 0` 的表述，确系对 SDK 分支逻辑的误判。Auditor 采纳 Developer 的质疑并执行更正。

## 3. 四阶段证明范围划分与修订判据

为避免将设计、符号、挂接和运行时行为混淆，Auditor 正式划定 CFI 证据链的四个证明阶段及其证据边界：

### 3.1 四阶段证明范围矩阵

| 阶段 | 证明范围（能证明什么） | 局限（不能证明什么） | 证据与判据要求 |
| --- | --- | --- | --- |
| **阶段一：源码与内核配置分析** | 目标内核启用了 `CONFIG_CFI_CLANG=y`；KernelPatch 框架具备 CFI 穿透跳板机制（`replace__cfi_slowpath` 经 `should_cfi_pass` 识别 KPM 内存）。 | 不能证明目标符号实际存在、地址正确或运行时 hook 成功。 | 目标内核配置声明、KernelPatch `secpass.c` 代码走查。 |
| **阶段二：符号地址解析** | 目标内核包含 `__cfi_slowpath` 或 `__cfi_slowpath_diag` 符号，并取得其实际地址 / KASLR 偏移。 | 不能证明 KernelPatch 加载器找到了该符号，亦不证明 hook 已建立。 | 目标内核镜像解包与反汇编、kallsyms 符号导出表检索。 |
| **阶段三：挂接成功（加载前条件）** | KernelPatch 初始化时成功获取有效 slowpath 地址，调用 `hook()` 成功且 `err == 0`。 | 不能证明当具体业务回调被内核间接调用时，`should_cfi_pass` 是否能正确放行。 | **否定判据**：dmesg 无 hook 报错日志、无 no symbol 警告；<br>**肯定判据（满足其一）**：<br>① 运行时日志 `__cfi_slowpath_diag resolved at runtime: <有效地址>` 且 `bypass_kcfi done: 0`；<br>② `patch_config` 预设命中证据且 `bypass_kcfi done: 0`；<br>③ KernelPatch 运行时已生效 hook 表项。 |
| **阶段四：真实 VFS 调用实测** | 内核 VFS 子系统通过函数指针间接调用 NoMount 注册的代理表回调（`read_iter`, `open`, `iterate_dir`, `lookup` 等）时，未触发 CFI Panic，读写与目录枚举正常。 | 属于动态端到端实测结果，证明穿透生效；但不能反向豁免加载前的阶段三前置检查。 | 真实设备测试报告、文件读取内容吻合、目录遍历成功、全程无 CFI Oops/Panic。 |

### 3.2 修订后的前置条件

撤销原报告 §3.5 中关于核验 `hook __cfi_slowpath_diag: ..., error: 0` 的判据。更正为：
> **修订前置条件**：Tester 在嵌入加载 NoMount 前，必须绑定实际 KP 与 boot 身份，依据阶段三要求核实挂接直接证据（否定日志缺席 + 肯定证据具备任一）；若测试现场受限无法取得直接挂接证据，须如实将 CFI 前置条件标为「未验证」，并同步扣减判据计数，措辞仅使用「未观察到」，严禁臆断。
