## 3. 加载事件契约独立审查

### 3.1 审查事实与控制流走查

在 `nomount 0.3.1`（源码 `d33eaf8`）中，入口初始化函数 `nomount_init` 定义如下：

```c
static long nomount_init(const char* args, const char* event, void* reserved) {
  if (args && *args)
    return -EINVAL;
  int rc = nm_prepare_control_engine();
  if (rc) {
    pr_err("NoMount: initialization failed: %d\n", rc);
    nm_cleanup_control_engine();
    return rc;
  }
  nm_initialized = true;
  return 0;
}
```

相较于 0.3.0 初版，原代码中 `if (event && !strcmp(event, "pre-kernel-init")) return -EAGAIN;` 的硬性拒绝分支已被彻底移除。

### 3.2 契约判断结论

1. **默认嵌入时机成立**：
   KernelPatch 在开机引导阶段加载嵌入式 KPM 时传递 `event = "pre-kernel-init"`；在系统启动后动态加载时传递 `event = "post-kernel-init"`。
   当前代码对 `event` 取值做非歧视处理，**默认 `pre-kernel-init` 与 `post-kernel-init` 均被模块入口允许**。
2. **加载事件不决定准备流程**：
   `event` 字符串不传递给下游准备函数，`nm_prepare_control_engine()` 执行确定性的四步初始化流程（backing 查询 -> BTF 布局 -> 管理互斥锁 -> 注册 keyring 控制通道），不随事件取值改变准备行为。
3. **失败路径防御性清理**：
   在 `nm_prepare_control_engine()` 中：
   - 若任一准备步骤返回非零错误码，立即执行回滚：
     - 若管理互斥锁已分配，调用 `nm_discard_management_mutex()` 释放；
     - 重置 `nm_topology_ready = false`；
     - 清空 `nm_backing_open_permission = NULL`；
     - 调用 `nm_discard_directory_view()` 销毁未发布的目录视图缓存；
   - 最关键的对外发布入口 `nm_register_control()`（向系统注册 keyring）位于最后一步，若前期失败，外部不可见未完成结构，不会造成半初始化悬挂。
4. **技术限制与同源风险声明**：
   - `test_load_events.py` 为 Developer 宿主单测 Oracle，其通过只能证明模块在 Mock 环境下逻辑无误；
   - 在真机环境下，`pre-kernel-init` 触发于内核极早期，部分厂商内核在此阶段 BTF、kallsyms 或 VFS 互斥锁可能尚未完全就绪；
   - 因此，**代码层允许 `pre-kernel-init` 不等于保证所有目标设备在极早期均能初始化成功**，此项必须由 Tester 在真实设备上开展验证。
